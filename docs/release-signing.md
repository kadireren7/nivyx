# Release signing (maintainer procedure)

`nivyx update` can check that a release was signed by the project's
offline key before it unpacks or runs anything it downloaded. This page is
the complete procedure. **As of this writing no production key exists and
`scripts/release-keys.txt` is empty, so the check is not enforced**; updates
work exactly as before (SHA-256 against `SHA256SUMS` only) and say
`release signatures are not checked yet`.

Nothing here may be done on a CI runner or any online machine, and no
private key, passphrase or signature-producing secret is ever committed,
uploaded or shared. Temporary keys generated by the test suite exist only
inside a test run and are deleted with it.

## What is signed and checked

Every release (`.github/workflows/release.yml`) contains
`nivyx-release.manifest`:

```
nivyx-release-manifest 1
product nivyx
version 2.4.0
commit <git revision the release was built from>
sha256 <hex> nivyx-2.4.0.spdx.json
sha256 <hex> nivyx-linux-x86_64.tar.gz
sha256 <hex> nivyx-macos-arm64.zip
sha256 <hex> nivyx-macos-x86_64.zip
sha256 <hex> nivyx-windows-x86_64.zip
```

The maintainer signs it offline and uploads `nivyx-release.manifest.sig`:
one line per signature, `ed25519 <key id> <base64 signature>` (the key id
is the first 8 bytes of SHA-256 of the raw public key, in hex).

An updater that carries at least one key (`scripts/nivyx`,
`scripts/macos/nivyx`, `scripts/windows/nivyx-impl.ps1`, between `BEGIN/END
RELEASE KEYS`) refuses the update, and changes nothing, unless all of this
holds:

1. the release has both files (missing → `is not signed`);
2. the **installed** engine (`dpi-proxy --verify-release`, OpenSSL Ed25519,
   no OpenSSL configuration read) finds a valid signature by a carried key
   (otherwise `signature is not valid`);
3. the manifest is format 1, for product `nivyx`, with one `version` line
   equal to the version the release announces (otherwise `refusing a
   substituted or replayed release`) and newer than the installed version
   (otherwise `refusing a downgrade`);
4. the manifest's SHA-256 for the downloaded archive matches it (otherwise
   `does not match the signed manifest`).

Old updaters (v2.3.0 and earlier) do not know these files and ignore them;
only updaters that carry a key enforce them. An old release served as
"latest" is never installed (it is not newer), and a release published
without a signature is refused by every updater that carries a key.

What it does not protect against: a compromised signing key (see
rotation), an attacker who withholds updates (a user who never receives a
newer release is not told), and the first install (the downloaded ZIP or
checkout is trusted as obtained; verify it with `SHA256SUMS` and `gh
attestation verify`, see docs/security.md).

## 1. One-time key setup (offline)

Needs: an offline machine (not used for browsing, no network while the key
is present), the OpenSSL 3 command-line tool (`openssl version` must say
`OpenSSL 3.x`, not LibreSSL; on macOS use Homebrew's
`$(brew --prefix openssl@3)/bin/openssl` and `export OPENSSL=...`), a copy
of this repository, and two removable media.

Create **two** keys: a primary for signing releases and a recovery key
that is never used unless the primary is lost or compromised. Each is
encrypted with its own strong passphrase:

```sh
umask 077
openssl genpkey -algorithm ed25519 -aes-256-cbc -out nivyx-release-primary.pem
openssl genpkey -algorithm ed25519 -aes-256-cbc -out nivyx-release-recovery.pem
```

Get the public key lines and their ids (prompts for each passphrase):

```sh
scripts/release-sign.sh pubkey nivyx-release-primary.pem  nivyx-release-2026-primary
scripts/release-sign.sh pubkey nivyx-release-recovery.pem nivyx-release-2026-recovery
scripts/release-sign.sh keyid  nivyx-release-primary.pem
```

Storage: the primary on one removable medium (plus an encrypted backup
copy in a second place), the recovery key on another, kept apart from the
primary; passphrases stored separately from the media (e.g. a password
manager or sealed paper). Delete the `.pem` files from the offline
machine afterwards. Record the key ids, creation dates and where each copy
is.

## 2. Enable enforcement (a normal commit, on an online machine)

Only the two **public** lines leave the offline machine. Append them to
`scripts/release-keys.txt`, then:

```sh
scripts/release-keys.sh sync    # writes them into the three updaters
scripts/release-keys.sh check   # what CI checks
scripts/release-keys.sh list    # key ids, to compare with your record
```

Commit and release as usual. From that release on:

- the release workflow creates the release as a **draft** (see 3);
- users who installed or updated to it get an updater that refuses any
  later update without a valid signature. Users of older versions are not
  affected until they install a version that carries the key.

Before the first enforced release, run the release dry run (`Actions →
release → Run workflow`) and sign its `release-assets` artifact as a
rehearsal (step 3 without uploading).

## 3. Every release

1. Bump `VERSION`, commit, push the tag `v<VERSION>`. The workflow runs the
   whole CI matrix, assembles the release, tests the final files, attests
   provenance and creates a **draft** release containing
   `nivyx-release.manifest` (no `.sig`). A draft is not visible to
   `nivyx update`.
2. Download the draft's files on an online machine and check them:

   ```sh
   mkdir rel && cd rel
   gh release download v<VERSION> --repo kadireren7/nivyx
   sha256sum -c SHA256SUMS
   for f in nivyx-*; do gh attestation verify "$f" --repo kadireren7/nivyx --source-ref refs/tags/v<VERSION>; done
   ```

3. Copy the folder (not the key) to the offline machine, insert the
   primary key medium, and sign. `release-sign.sh release` checks that the
   manifest is for that version and matches every file, signs with the
   primary key, and verifies the result with OpenSSL against
   `scripts/release-keys.txt` (it refuses a key that is not listed there):

   ```sh
   scripts/release-sign.sh release /media/primary/nivyx-release-primary.pem rel <VERSION>
   ```

4. Remove the key medium. Copy only `rel/nivyx-release.manifest.sig` back,
   then upload it and publish:

   ```sh
   scripts/release-sign.sh verify scripts/release-keys.txt rel/nivyx-release.manifest
   gh release upload v<VERSION> rel/nivyx-release.manifest.sig --repo kadireren7/nivyx
   gh release edit v<VERSION> --draft=false --latest --repo kadireren7/nivyx
   ```

5. Check from an installed machine: `sudo nivyx update` on a machine with
   the previous version must print `Release signature verified (ed25519 key
   <id>)`.

If a signature step fails, do not publish the draft. A published release
without a valid `.sig` is refused by every updater that carries a key (it
fails closed); fix it by uploading a correct `.sig`.

## 4. Key rotation (planned)

1. Generate the new key offline (as in 1) and add its public line to
   `scripts/release-keys.txt` **next to** the current ones; release
   version N signed with the current primary. Updaters from N trust both.
2. Wait until most users have N (old updaters that do not know the new key
   would refuse releases signed only by it). Releases can carry two
   signatures meanwhile: sign with both keys
   (`APPEND_SIGNATURE=1 scripts/release-sign.sh release <new key> rel <VERSION>`
   after the first signature).
3. Remove the retired key's line in a later release (still signed with a
   key the previous release trusts).

Keep at least one key that the previous released updater trusts on every
release: the chain must never break.

## 5. Recovery

- **Primary lost, not compromised:** sign the next release with the
  recovery key (it is already trusted), add a new recovery key in that
  release, and treat the old recovery key as the new primary (or rotate
  as in 4).
- **Primary compromised:** sign a release with the recovery key that
  removes the compromised key from `scripts/release-keys.txt` and adds a
  new one; publish an advisory (GitHub Security Advisory + release notes)
  telling users to update now. Until a user installs that release, their
  updater still trusts the compromised key; this cannot be fixed remotely.
- **Both keys lost or compromised:** updaters that carry only those keys
  can no longer be updated automatically. Ship a release with new keys
  and tell users to reinstall manually from the release page (Linux: `git
  pull && sudo ./scripts/install.sh`; macOS/Windows: download the ZIP,
  check it against `SHA256SUMS` and `gh attestation verify`, run the
  installer). Settings and learned state are kept by a reinstall.

## Tests (temporary keys only)

- `scripts/release-verify-test.sh` — the engine's check: valid, missing,
  modified, wrong key, rotation, malformed input, hostile OpenSSL
  configuration (Linux, macOS, Windows CI).
- `scripts/signed-release-cases.sh` — builds the same 8 mock releases for
  every platform; run on real installs by `update-signature-test-linux.sh`,
  `scripts/macos/update-test.sh` and `scripts/windows/update-signature-test.ps1`:
  every bad case is refused and changes nothing; the valid one installs
  and keeps settings and learned state; with no key configured, updates
  work as before.

The test override `NIVYX_TEST_RELEASE_KEYS` replaces the carried keys only
together with `NIVYX_RELEASE_API`, which must point at 127.0.0.1/localhost.
